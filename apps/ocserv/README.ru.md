# Корпоративный VPN

Шлюз использует ocserv 1.6.0. Профиль задаёт разрешённые IPv4-подсети. В PL администратор связывает профиль с идентификатором сотрудника и при необходимости задаёт срок доступа. Записи и журнал сохраняются в отдельном томе шлюза.

## Настройка шлюза

В каталоге установки PL создайте `modules/ocserv/operator/` от имени root с правами 0700. Поместите в него `server.crt` с цепочкой TLS и `server.key` с правами 0600. Пример `gateway.json` для отдельного клиентского пула.

```json
{"name":"Удалённый доступ","auth_mode":"certificate","pool":"10.77.0.0/24"}
```

Пул используется для адресов клиентов. Выберите свободную IPv4-подсеть от /8 до /29, отдельную от корпоративных сетей, сетей Docker и площадки.

Для режима `certificate` добавьте `ca.crt` с доверенным CA клиентских сертификатов. Назначение сотрудника в PL сопоставляется с его уникальным CN. Используйте отдельный CA для VPN и назначайте разные CN сотрудникам. Идентификатор занимает до 62 ASCII-знаков. Выдавайте сертификаты с назначением TLS Web Client Authentication.

### Вход через Dex и другие OIDC-провайдеры

Для Dex 2.46.1 зарегистрируйте статический OIDC-клиент с адресом возврата `https://vpn.example.test/sso/callback`. В `gateway.json` укажите `"auth_mode": "oidc"`. Рядом поместите `oidc.json` с правами 0600. Укажите внешний issuer Dex целиком, включая его путь, и тот же `client_id`, что в Dex. Для конфиденциального клиента добавьте в файл его `client_secret`.

Пример для issuer `https://id.example.test/dex` и клиента `pl-vpn`.

```json
{
  "openid_configuration_url": "https://id.example.test/dex/.well-known/openid-configuration",
  "client_id": "pl-vpn",
  "user_name_claim": "sub",
  "redirect_uri": "https://vpn.example.test/sso/callback",
  "required_claims": {"iss": "https://id.example.test/dex", "aud": "pl-vpn"}
}
```

Для HTTPS шлюз использует доверенные CA Debian. Если у провайдера своя PKI, положите её публичный CA или цепочку CA в PEM-формате в `operator/idp-ca.pem`. В PL выдайте профиль идентификатору `sub` этого сотрудника у провайдера. Требования к MFA задаются у провайдера.

Dex 2.46.1 выпускает подписанный ID-токен без заголовка `typ`. В браузерном входе OpenConnect шлюз принимает такой токен после проверки подписи по ключу провайдера, издателя, аудитории, срока действия, обязательных полей и совпадения `nonce` с запросом входа. Если провайдер передал `typ`, шлюз принимает только строку `JWT`.

### Публикация шлюза

Для публикации добавьте принадлежащий root файл `modules/ocserv/ingress.json` с правами 0600. Пример для локального стенда.

```json
{"address":"127.0.0.1","port":4443}
```

Адрес должен принадлежать хосту PL. На нём публикуются TCP (TLS) и UDP (DTLS). Примените изменения в файлах оператора выключением и включением модуля. Без `gateway.json` доступно администрирование профилей и назначений. Клиенты подключаются только после настройки шлюза и публикации порта.

## Доступ к сетям

Шлюз посылает клиенту маршруты его профиля и независимо проверяет пересылаемые пакеты через nftables в собственном сетевом пространстве. Каждая сессия привязана к выданному адресу и TUN-интерфейсу. Разрешённый трафик к корпоративным адресам проходит с подменой исходного адреса шлюзом. Узлу PL нужен собственный маршрут к каждой разрешённой подсети. Доступ к самому VPN-контейнеру, обмен между VPN-клиентами и пересылка IPv6 через туннель закрыты.

Изменение разрешений, отзыв или истечение срока закрывают действующие подключения сотрудника и аннулируют его cookies. Правило nftables с ограниченным сроком перестаёт пропускать пакеты в момент окончания допуска. Администратор также может завершить одну сессию, сохранив назначение для нового входа.

Управление выполняет PL через локальный контроллер по ID принадлежащего ему контейнера. Образ включает ocserv, occtl и сведения о соответствующих исходниках в `/usr/share/pl/provenance/ocserv/`.
