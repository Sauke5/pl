# Разработка и выпуск общего интерфейса PL

PL portable source, 05.11.2026. Применяется к собственным текущим и будущим приложениям. Визуальный эталон — Платформа; нативные интерфейсы сторонних продуктов остаются у их владельцев. Этот документ определяет выбор способа реализации и доставки, но не выдаёт разрешение на production. При остановке пользователем дальнейшие runtime-изменения прекращаются; уже применённый результат фиксируется отдельно от подготовленных кандидатов.

## 1. Перед изменением определить владельца и способ доставки

Сначала прочитать branch/status/diff и затронутый код. До сборки, делегирования сборок и подготовки production writer составить короткую таблицу: изменение → owning source → фактический URL/импорт → владелец runtime → необходимое действие. Проверить активный HTML/шаблон и настройки режима. Наличие файла в repository/image само по себе не означает, что браузер его использует.

| Изменение | Единственный источник | Обычная доставка |
| --- | --- | --- |
| Название темы, палитра, фон и тематический декор | `frontend/public/ecosystem/theme-catalog.json`, `theme-menu.css` | Один выпуск центральных assets Платформы |
| Поведение меню тем | `frontend/public/ecosystem/theme-runtime.js` | Центральный выпуск с проверкой совместимости API |
| DOM-каркас, общий CSS, примитивы, React adapter | `frontend/packages/pl-ui` | Версионированная библиотека; только реально затронутые consumers |
| Предметный экран, его таблица, редактор, маршрут | Source соответствующего приложения | Выпуск только owning frontend/сервиса |
| Gateway/auth/finite route | Source Платформы и конкретный wire contract | Отдельная адресная интеграция; не требуется ради смены цветов |
| Подтверждённый автономный вход | Та же библиотека и точные копии общих assets | Отдельная доставка только этому входу при наличии его в scope |

План первого перехода всей экосистемы на общий UI не является планом каждой последующей правки. Не назначать выпуск всех сервисов только из-за слов «общий интерфейс» или «во всех приложениях».

## 2. Фактическая доставка тем

Integrated приложения используют origin Платформы и абсолютные адреса:

- `/ecosystem/theme-catalog.js` — сгенерированный каталог;
- `/ecosystem/theme-runtime.js` — общий `PLTheme`;
- `/ecosystem/theme-menu.css` — меню и общий тематический декор.

Конкретный набор подключённых consumers устанавливать по текущим HTML, шаблонам и build-конфигурации выбранного релиза. В portable core `/ecosystem/` обслуживает web. Совпадение source-файлов не доказывает, что отдельный consumer их загружает.

Integrated и standalone — разные способы доставки. Если автономный вход существует и включён в задачу, его собственные assets обновляются отдельно. `npm --prefix monitoring/source/it-portal/frontend run ui:build -- --standalone` явно синхронизирует source-копии админок; обычный `ui:build` работает только с frontend public. Для других приложений смотреть их build contract и закреплённый vendor package. Не добавлять standalone-режим по образцу другого сервиса без потребности.

Если запрос «во всей экосистеме» не различает канонические и автономные входы, сначала перечислить найденные режимы и установить границу задачи. Центральный выпуск не объявлять обновлением автономного origin; наличие старого локального порта не делает его обязательным объектом каждой косметической правки.

## 3. Алгоритм изменения темы

Шаги runtime-выпуска ниже выполняются при действующем разрешении пользователя на соответствующий объём. Подготовка source и artifacts сама такого разрешения не создаёт; уже данное в задаче разрешение не запрашивать повторно.

1. Менять каталог и общий декор в центральном source. Сохранять стабильный ID и `localStorage["pl-ui-theme"]`; для «Хэллоуина» ID остаётся `night`. Палитровые bridges приложений используют общие tokens; новые дубли theme controller, локальные overrides и копии skeleton не создавать.
2. Выполнить `python3 -B monitoring/source/it-portal/deploy/build-theme-catalog.py`, затем `--check` из Git root. Если затронуты distribution assets, выполнить `npm run ui:build`/`ui:check` в frontend: это синхронизация только локальных public UI assets. Python generator не включается в core prebuild; внешние report bridges выбираются исключительно `--reports-root PATH`.
3. Проверить затронутое поведение: сохранение/reload/cross-tab, меню, читаемость и смысловые статусы; для декора — отсутствие перехвата ввода, overflow, reduced motion и влияние на legacy темы. При изменении startup — Chromium/WebKit с реальным CSP. Проверки бизнес-записей, реальных scans/imports/jobs ради темы не запускать.
4. Собрать immutable центральный web artifact из принятого source. В текущем runtime `/ecosystem/` обслуживает web Платформы, поэтому достаточно его адресного обновления через полную effective Deployment-модель и существующий entrypoint. Если будущий runtime вынесет assets в отдельный сервис, обновлять фактического владельца, установленного шагом 1.
5. Сохранить предыдущий image/pin и проверить, что model diff ограничен выбранным image. Backend/API, БД, worker, gateway manifest, nginx routes, ACL и зависимости consumers ради такой правки не обновлять. Обновление контейнера, содержащего app frontend и локальные копии, не требуется, если integrated HTML эти копии не загружает.
6. После одного центрального выпуска проверить public status/MIME/SHA изменённых файлов, их соответствие source и cache headers. Для стабильных URLs нужен `no-cache`/revalidation; при старом оформлении сначала установить, какая версия была загружена браузером. Открытая страница обычно перечитывает CSS/JS после reload; автоматическую замену ресурсов в уже открытой вкладке не обещать.
7. Подтвердить центральные refs у затронутых consumers и выполнить ограниченный browser smoke на представительном integrated экране. Проверка refs/SHA не подменяет визуальную проверку. Не выдавать HTTP200 за business acceptance; не перезапускать приложение для «подтягивания темы» при доказанной центральной доставке.
8. Если автономный вход включён в задачу, отдельно перечислить его URL, фактические local files и минимальный способ доставки; только затем готовить его artifact. При отсутствии такого входа в scope остановиться на integrated результате, не готовить все standalone overlays по умолчанию.
9. Зафиксировать actual image/source/SHA и выполненные проверки в receipt и согласованной ветке релиза. Отдельно перечислить неприменённые кандидаты и исключения. Source sync не пересоздаёт сервисы.

## 4. Алгоритм изменения каркаса и общих компонентов

1. Найти реализацию в `@pl/ui` 1.0.2-pl.1 (`frontend/packages/pl-ui`): `core.js`, `styles.css`, `react.tsx`, primitives/dialog. Исправлять её один раз; приложение передаёт context/menu/content/callbacks через slots.
2. Установить, что реально меняется: общий CSS, DOM-поведение, API/props либо app adapter. React adapter импортирует `core.js` в bundle; React consumers также могут включать CSS/примитивы в собственную сборку. Центральный CSS или JS нельзя объявлять универсальным hot-update для уже встроенного npm-кода.
3. Составить точный список consumers по импортам и runtime refs. HTML consumers используют `/ecosystem/ui-v1.js`/`ui-v1.css`: при изменении `core.js` выполнить `ui:build` и включить новый browser JS в центральный выпуск, при изменении `styles.css` так же выпустить browser CSS. Изменение только React adapter не требует замены HTML core. React consumers, использующие изменённый bundled код, требуют принятой новой версии пакета и пересборки. Не пересобирать сервисы, которых diff не касается.
4. Если содержимое уже выпущенного npm package изменено, поднять package version и выпустить новый immutable tarball с SHA/lockfile. Нельзя менять bytes под старой версией. Чистая правка внешнего каталога/декора темы не меняет `@pl/ui` и не требует package bump.
5. Проверить общий shell и реальные adapters: geometry, бренд, collapse/persistence, slots, focus/keyboard, logout pending/error, loading/error/fallback; сохранить предметные страницы и guards. Порядок загрузки и CSSOM readiness проверять в WebKit. Для старых app styles исключить вмешательство в shared shell, а не добавлять ещё одну несогласованную оболочку.
6. При совместимом API выпустить central browser assets и только необходимые обновления bundles. При несовместимом контракте подготовить явный переход версий; не заменять содержимое v1 так, чтобы сломать ещё работающий consumer.
7. Сохранять старые hashed app assets для открытых вкладок. При новых конечных asset paths изменить allowlist только для них; сама тема по прежним URLs не требует новых routes. Проверить параллельную загрузку через gateway при изменении доставки, сохранив общие bounded lanes и auth.
8. Каждый выбранный runtime обновлять один раз с полным model diff и сохранением env/mounts/security/невыбранных IDs. Это управляемый выпуск затронутых frontend, а не обязательный релиз всей экосистемы.

При изменении только предметного экрана сохранить текущий shared shell и выпускать owning app. Необходимость нового persistence/API устанавливается по задаче и текущему контракту; UI-правка сама по себе не разрешает schema migration или смену архитектуры. Для предметных компонентов следовать правилам owning app. Смена темы автономного Wayline сохраняет существующий auth owner и не означает изменение auth или выполнение реального login/logout без соответствующей задачи.

## 5. Новое приложение

1. Проверить существующий scaffold и UI/SSO contracts. Выбрать integrated mode по умолчанию, route-prefix и права. Stack выбирать по задачам продукта и существующей архитектуре; не переписывать backend только для общего вида.
2. Подключить центральный каталог/runtime/menu CSS до первого рендера. Использовать `PlatformShell` из общего пакета либо `PLUI.createShell`; контекстное меню и рабочую область заполнять через slots. Для страниц без навигации использовать облегчённый shell. Собственные реализации логотипа, collapse, темы и профильного блока не копировать.
3. Сохранить единые browser preferences, подтверждённую identity, общий logout и предметные ACL. Нативный сторонний UI не оборачивать переделкой под этот алгоритм.
4. Проверить реальный prefix, startup, состояния, меню, theme/collapse/reload и основные предметные controls; зафиксировать готовность frontend отдельно от регистрации каталога и backend health.
5. Включить в AGENTS/README нового проекта ссылки на этот workflow, service onboarding и UI-контракт, чтобы следующий разработчик находил owning source и способ доставки.

## 6. Чего не считать доказательством необходимости выпуска

- Vendored assets обновились в source → это ещё не необходимость менять работающий integrated контейнер.
- В image есть старая копия темы → она может не использоваться браузером.
- Старый receipt перечисляет десять приложений → это граница того выпуска, не текущего изменения.
- Build прошёл или health200 → это не подтверждение фактической загрузки новой темы.
- Все Git HEAD совпали → это не доказательство runtime deployment.

Перед передачей задачи исполнитель сообщает owning source, реальный путь доставки, diff, нужные runtime и доказательства. Интегратор убирает из плана ненужные сборки до их запуска. Полные UI/SSO contracts остаются источником размеров, поведения и доступа; этот workflow определяет порядок работы.
