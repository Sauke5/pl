# Доставка модулей и обновления PL

Первоначальная установка содержит API, web и PostgreSQL. Каталог модулей получает
версии из подписанного каталога релизов; образы выбранного модуля скачиваются
host-controller при установке через web. Остальные образы не загружаются.
Действующие экземпляры продолжают использовать свои проверенные образы.

## Доверие и границы управления

Каталог публикуется как Ed25519 envelope с полями `payload` и `signature` в base64.
Публичный ключ закреплён в первоначальном пакете. Проверяются подпись, монотонная
`sequence`, совместимость `core_api`, архитектура, URL выбранного GitHub repository,
размер и SHA256 артефакта. Для каждого загруженного образа дополнительно сверяются
content ID, архитектура и provenance labels. Если в каталоге указан `expires_at`,
после истечения срока новые операции требуют свежего подписанного каталога.

Браузер передаёт идентификатор операции и опубликованную версию. Он не задаёт
download URL, Docker arguments, команды или пути файлов. API и web не получают
Docker socket. Администрирование выполняет локальный controller через
аутентифицированный Unix socket.

Неизменяемый `controller-supervisor.py` первоначальной установки проверяет
выбранный пакет и запускает активную версию controller. Обновлённые файлы
controller и модулей могут доставляться обычным подписанным релизом с совместимым
`core_api`. Замена закреплённого ключа этим протоколом не разрешается.

## Канал загрузки GitHub

Администратор задаёт профиль через web PL и проверяет доступ к подписанному
каталогу перед сохранением. Поддерживаются режимы `direct`, `external` и `xray`.
Профиль применяется к трём видам загрузок: каталог, core и модуль. Все redirect и
переходы на GitHub CDN используют тот же канал. При ошибке выбранного proxy
прямой fallback не выполняется.

`external` поддерживает HTTP CONNECT и SOCKS5 с DNS через proxy. Администратор
задаёт host/port, при необходимости username/password и отдельный CA. Проверка
TLS и имени GitHub/CDN сохраняется. Этот CA относится к доставке GitHub; AD и
внешние интеграции имеют собственные настройки доверия.

Credentials передаются в body аутентифицированного запроса. Сохранённый профиль
находится в `private/delivery-proxy.json`: root-owned regular file, mode `0600`.
Status возвращает параметры подключения и признак сохранённого пароля; test
сообщает результат проверки и версию каталога. Значения password/PEM в ответах
отсутствуют. Проверка читает фиксированный каталог,
проверяет Ed25519-подпись, expiry и sequence и не сохраняет проверяемый профиль,
пароль или каталог.

Сохранённый пароль можно оставить только для прежнего endpoint и username.
При смене адреса или учётной записи пароль задаётся заново. Для работы без
авторизации администратор явно выбирает этот режим; сохранённый пароль удаляется.

`xray` выбирает существующие installation-owned instance и inbound. Controller
использует текущие проверенные параметры этого inbound. Xray должен быть уже
установлен и включён; его первоначальное получение требует работающего прямого
или внешнего канала первоначальной доставки. Запущенный отдельно local Xray
подключается в режиме `external` по `127.0.0.1` и порту HTTP/SOCKS5 inbound.

Первоначальный `get-pl.sh` использует прямую загрузку. Параметр
`--download-proxy-file` в `install.sh` остаётся отдельным HTTP-only профилем первоначальной
загрузки; он не сохраняется как web-профиль доставки установленной PL.

## Настройки установленной платформы

В настройках PL администратор меняет публичный HTTPS-адрес, адрес прослушивания,
порт из URL, разрешённые сети/порты исходящих интеграций, серверный TLS-сертификат
с ключом и отдельные сертификаты доверия для исходящих HTTPS-соединений. Корневые
системные сертификаты остаются доступными; пустой custom outbound bundle убирает
дополнительное доверие. Проверка TLS не отключается. Настройки AD имеют собственный
CA и не используют этот bundle автоматически.

Настройки защищены `revision` и UUID операции. Хост проверяет принадлежность bind IP,
занятость порта, действительность/SAN сертификата и соответствие ключа. Приватный
ключ хранится в root-private файле и не возвращается в API. В ответах присутствуют
публичные настройки, публичный outbound CA и безопасное состояние операции.

Применение запускает отдельный worker. Для изменения core-конфигурации сохраняются
предыдущие config/state/TLS/CA; API и web пересоздаются без изменения БД и auth.
Runtime environment, HTTPS binding и HTTPS health читаются после применения. При
ошибке возвращаются предыдущие адрес, доверие и конфигурация. Новый адрес сообщается
до переключения, поэтому открытая на старом origin страница может показать ссылку
для повторного входа.

Изменение origin/TLS, затрагивающее локальные модули, использует проверяемый
`module-origin.py` и полный снимок всей установки перед изменением их состояния
или данных. Если подходящего переноса нет, preflight отказывает до изменений и
указывает затронутые модули. Прерванная настройка восстанавливается тем же штатным
`delivery.py recover`, который по журналу выбирает полный или конфигурационный
снимок. Installation root, identity и версия Docker/ОС этим интерфейсом не меняются.

## Обновление используемой установки

Администратор проверяет новую версию и запускает её установку в настройках PL.
Проверка каталога также обновляется в фоне при обращении к интерфейсу. Обновление
выполняет отдельный transient systemd service, который переживает перезапуск
host-controller. Журнал находится в `state/delivery/operation.json`.

Для новой операции в журнале фиксируются `worker_version` и
`worker_manifest_sha256` проверенного активного host package. Восстановление
выбирает эту же версию worker. Первоначальный supervisor и release key остаются
неизменным якорем доверия.

Для перехода со старого updater подписанный bootstrap может передать управление
целевому worker до остановки контейнеров и создания снимка. Проверяются текущая
операция, исходная и целевая версии, полные hashes пакетов и закреплённый ключ.
Передача сохраняет процесс и systemd unit, а журнал `worker_handoff` связывает
прежний worker с новым. Для восстановления выбирается фактически записанный
`worker_version`; версия установленного core может отличаться от версии worker.

До подтверждения установки интерфейс показывает описание версии из подписанного
каталога: пользу обновления, новое, улучшения и исправления. Автор релиза готовит
этот текст для пользователей в `docs/releases/VERSION.json` и передаёт его signer
через `--notes-file`. Описание подписывается вместе с каталогом.

Необязательное поле `release_notes` содержит `version`, `title`, `summary` и
`sections`. Каждая секция имеет `kind` (`new`, `improved` или `fixed`) и список
`items` с `title` и `description`. Версия описания соответствует версии каталога.
Старые schema-1 клиенты игнорируют дополнительное поле; каталоги без описания
остаются совместимыми. Публичный source export включает только JSON из
`docs/releases/` с именем по SemVer; внутренние документы разработки не включаются.

Перед применением новой версии проверяется пакет и загружаются образы. Затем PL
останавливает свои core и локальные модули, создаёт полный согласованный снимок
собственных данных и только после этого запускает новую версию API с migrations.
Снимок содержит все принадлежащие установке local Docker volumes, auth, конфиги,
ключи, состояние и данные модулей в installation root. UID/GID, permissions,
hard links, symbolic links и extended attributes сохраняются. Используемые
внешние сервисы не останавливаются; их собственные данные в снимок PL не входят.

Ручной ICMP входит в обычный core. При добавлении или изменении helper сохраняются
его внешние файлы, policy и состояние собственных systemd units. Откат возвращает
эти файлы и состояние до восстановления дерева установки. Установленный через
системный package manager `hping3` остаётся в ОС; общие пакеты не удаляются.

После запуска проверяются core, ранее работавшие контейнеры модулей и новый
host-controller. При ошибке восстанавливается предыдущий снимок данных вместе
с предыдущими образами и controller. Возврат образа отдельно от БД не используется
как rollback schema. Смена PostgreSQL major и несовместимый `core_api` этим путём
не выполняются.

Снимки находятся в `private/upgrade-backups/<operation-id>` и содержат приватные
данные установки. Они сохраняются после операции для восстановления и не входят
в публичную поставку. Текущий `maintenance.py` имеет отдельный core-only контракт;
его ограничения на установку с локальными модулями сохраняются.

Размер core-архива включает готовые образы API, web и PostgreSQL. Публичный архив
исходников содержит выбранные исходные файлы и manifest. Для PL 0.3.3 это были
149,1 MiB core и 4338 исходных файлов: вместе с manifest 35,6 MB до архивирования
и 6,8 MiB с gzip 9. Для других версий размеры определяются их фактическим составом.

## Прерванная операция

Worker lock и состояние systemd service отличают выполняющуюся операцию от
прерванной. При отсутствии worker незавершённая операция переходит в
`recovery_required`; новые изменения модулей блокируются. Если web доступен,
восстановление запускается из настроек PL с тем же идентификатором операции.

Если остановленный core делает web недоступным, администратор использует
доверенный worker из `state/delivery/operation.json`, поле `worker_version`.
Для legacy-операции без этого поля берётся `version` из
`state/controller-supervisor.json`:

```sh
sudo python3 /opt/pl/releases/WORKER_VERSION/delivery.py recover \
  --root /opt/pl --operation-id OPERATION_UUID
```

Root, версия worker и UUID заменяются на проверенные значения своей установки.
Worker другой версии не подставляется вместо записанного при повреждённых или
отсутствующих файлах. При отсутствии завершённого
`snapshot.json` частичный архив не восстанавливается: schema-changing стадия ещё
не разрешалась, и helper возвращает в работу предыдущую установку. Готовый снимок
проверяется целиком перед восстановлением. При ошибке восстановления архивы и
журнал сохраняются для повторного штатного восстановления.
