# PL: установка и подготовка исходников

Новая установка загружает только API, web и PostgreSQL. Модули устанавливаются из web PL по мере необходимости; их образы отсутствуют в core-архиве.

## Быстрый запуск

На Ubuntu или Debian:

```sh
curl -fsSL https://raw.githubusercontent.com/Sauke5/pl/main/installer/get-pl.sh | sudo sh -s -- --production
```

Bootstrap проверяет Ed25519-подпись каталога, размер и SHA256 пакета. Адрес HTTPS определяется автоматически. Для собственного домена можно заранее сохранить скрипт и передать его явно:

```sh
curl -fsSLo get-pl.sh https://raw.githubusercontent.com/Sauke5/pl/main/installer/get-pl.sh
sudo sh get-pl.sh --production --public-url https://pl.example.test
```

Если GitHub доступен через прокси, передайте его и `curl`, и установщику.
Для HTTP CONNECT:

```sh
curl -fsSL --proxy http://PROXY_HOST:PORT https://raw.githubusercontent.com/Sauke5/pl/main/installer/get-pl.sh | sudo sh -s -- --production --proxy http://PROXY_HOST:PORT
```

Для SOCKS5 с разрешением имён на прокси:

```sh
curl -fsSL --proxy socks5h://PROXY_HOST:PORT https://raw.githubusercontent.com/Sauke5/pl/main/installer/get-pl.sh | sudo sh -s -- --production --proxy socks5h://PROXY_HOST:PORT
```

Подойдёт соответствующий вход Xray или внешний прокси. `127.0.0.1` означает
сервер, на котором выполняется установка. Bootstrap использует прокси для
каталога, пакета PL и ключа Docker; системный apt сохраняет свой сетевой маршрут.
Проверка HTTPS-сертификатов сохраняется. Прокси будущих обновлений и загрузок
модулей настраивается отдельно в интерфейсе PL.

Логин и пароль передаются через `--proxy-user 'LOGIN:PASSWORD'` в обеих частях команды, как в curl:

```sh
curl -fsSL --proxy socks5h://PROXY_HOST:PORT --proxy-user 'LOGIN:PASSWORD' https://raw.githubusercontent.com/Sauke5/pl/main/installer/get-pl.sh | sudo sh -s -- --production --proxy socks5h://PROXY_HOST:PORT --proxy-user 'LOGIN:PASSWORD'
```

Для HTTP CONNECT замените `socks5h://` на `http://`. Пароль может содержать
двоеточия: разделителем служит только первое. Также поддерживается
userinfo в адресе `--proxy`: логин и пароль перед host; специальные символы
кодируются по правилам URL, например `@` как `%40`.
Не смешивайте userinfo и `--proxy-user`.

При необходимости вместо inline-параметров можно использовать приватный
JSON-профиль владельца root с правами `0600`:
`{"url":"socks5h://PROXY_HOST:PORT","username":"USER","password":"PASSWORD"}`.
Команда для заранее скачанного скрипта:
`sudo sh get-pl.sh --production --proxy-file /root/pl-proxy.json`.

Первый запуск создаёт самоподписанный TLS-сертификат. Доверенный сертификат можно загрузить в настройках PL. При повторном запуске установщик сохраняет существующий сертификат.

С `--production` новая установка создаёт администратора `admin` со случайным
паролем. Установщик сообщает путь к закрытому файлу, само значение в вывод не
попадает. Для стандартного root прочитайте его так:

```sh
sudo cat /opt/pl/private/initial-admin-password
```

После первого входа смените пароль в интерфейсе. Повторный запуск сохраняет
действующий пароль и данные; файл содержит только первоначальный пароль.
Для установки из готового пакета `install.sh --production --password-file PATH`
позволяет заранее выбрать пароль из закрытого файла длиной от 12 байт.

Без `--production` сохранён прежний режим совместимости с первоначальным
`admin / admin`. Новую установку для работы запускайте с `--production`.
Существующую установку с коротким seed этот флаг не переделывает и отклоняет;
возобновляйте её в прежнем режиме и меняйте пароль через PL.

Карточки, системы, внешние подключения, пользователи и Active Directory настраиваются в PL. Модули устанавливаются в каталоге; новые версии core проверяются и применяются в настройках. Для AD сохраняется проверка TLS и имени сервера. Приватный ключ шифрования credentials принадлежит установке и должен входить в её backup.

Перед подтверждением обновления PL показывает описание версии из подписанного каталога: какую пользу приносит обновление, что появилось, что улучшено и какие ошибки исправлены. Это авторское описание для пользователей, доступное на странице обновлений.

Кнопка «Обновить всё» запускает обновление Платформы, а после её готовности —
совместимых установленных модулей по одному. Оставьте вкладку открытой; после
перезагрузки страницы очередь продолжится. При ошибке она остановится и покажет
причину. Новые запуски обновлений сохраняются в «Событиях» и «Операциях» вместе
с инициатором, версией и результатом.

В «Настройки → Развёртывание» меняются адрес PL, интерфейс сервера, TLS-сертификат, разрешённые сети и порты источников и CA внешних HTTPS-интеграций. PL проверяет параметры перед применением и восстанавливает предыдущую конфигурацию при неудаче. Смена адреса установленного native-приложения выполняется вместе с его настройками и согласованным снимком данных.

Ручная диагностика входит в обычный core: ICMP, DNS, PTR, HTTP, TCP, TLS,
проверка выбранных портов и клиент iperf3. Компоненты ICMP подготавливаются
автоматически при установке и обновлении. Ограничения ICMP по IPv4-сетям меняются
в настройках развёртывания. Для измерения скорости на целевом сервере должен
работать iperf3-server; наличие клиента в PL не запускает сервер на проверяемом
устройстве.

## Доступ к GitHub для доставки

В настройках обновлений можно выбрать прямое соединение, внешний proxy или inbound существующего PL-модуля Xray. Этот профиль используется для каталога релизов, core-пакетов и модулей, включая переходы на GitHub CDN.

Внешний proxy поддерживает HTTP CONNECT и SOCKS5 с разрешением DNS через proxy. Укажите host и порт, при необходимости — логин, пароль и отдельный CA для этого канала. Перед сохранением проверьте доступ к подписанному каталогу. При ошибке выбранного канала доставка останавливается и показывает ошибку; прямого fallback нет. Пароль сохраняется на сервере в закрытом root-owned файле и не возвращается в ответах.

Режим Xray выбирает уже установленный и включённый модуль PL с подходящим inbound. Если Xray запущен на сервере отдельно, выберите внешний proxy, host `127.0.0.1` и порт его HTTP/SOCKS5 inbound. Для первого получения core и Xray нужен доступный начальный канал: прямой доступ или внешняя первоначальная доставка. Параметры дальнейшей доставки меняются через web PL.

## Сборка

Из корня репозитория с локальным Docker:

```sh
python3 installer/package.py context --output release/generated/pl-source.tar.gz
python3 installer/package.py build --source-archive release/generated/pl-source.tar.gz --version VERSION --output release/generated/pl-VERSION.tar.gz
```

По умолчанию `build` создаёт только core. Дополнительные исходники выбираются флагами `context --with-*`. Отдельный модуль собирается командой `module --module-id MODULE` из context с его исходниками; точные доступные имена и параметры показывает `python3 installer/package.py --help`.

```sh
python3 installer/package.py context --with-forms --output release/generated/pl-forms-source.tar.gz
python3 installer/package.py module --module-id forms --source-archive release/generated/pl-forms-source.tar.gz --version VERSION --output release/generated/pl-forms-VERSION.tar.gz
```

Артефакты immutable: существующий version/file не перезаписывается другой сборкой. Публичный каталог подписывается отдельным release key; приватный ключ не входит в исходники и образы. Смена PostgreSQL major и несовместимого протокола модулей требует отдельного перехода.

Core-архив включает три готовых Docker-образа: API, web и PostgreSQL. Отдельный архив публичных исходников обычно занимает несколько MiB. Например, в PL 0.3.3 core занимал 149,1 MiB; 4338 исходных файлов вместе с manifest — 35,6 MB до архивирования и 6,8 MiB с gzip 9. Размер зависит от версии; исходные файлы и manifest в сжатом архиве сохраняются побайтно.

## Проверки и восстановление

```sh
python3 -m unittest discover -s installer/tests
```

На macOS для canonical-path тестов используйте `TMPDIR=/private/tmp`. Go integration tests требуют отдельную PostgreSQL; frontend и component tests запускаются из соответствующего приложения. Unit tests не подтверждают установку или пользовательский сценарий.

Web upgrade создаёт согласованный snapshot установки, включая данные локальных модулей. При неудаче требуется возвращать и данные, и образы. Отдельная [утилита maintenance](maintenance.ru.md) сохраняет прежний ограниченный контракт backup/restore core и отказывает при локальных модулях; она не заменяет snapshot web upgrade.

Для полной установки с native-модулями предусмотрено [аварийное резервное копирование и восстановление](disaster-recovery.ru.md). `disaster-recovery.py` сохраняет данные, ключи, настройки и нужные образы. Cold restore возвращает ту же установку с прежними root, HTTPS-адресом и installation ID на подготовленном Linux. Архив и его SHA256 храните вне исходного сервера; установленная версия инструмента и руководство находятся в `ROOT/releases/VERSION/`.

Обе standalone-админки, host-agent и Reports доступны как исходные компоненты; они не устанавливаются вместе с core автоматически. Их размещение и доступ задаются для конкретной установки. File Auditor требует отдельной Windows-приёмки службы и сканирования.

Перед публичным экспортом новые выбранные исходники должны быть добавлены в Git index: exporter использует тот же allowlist, что и source builder. `python3 installer/public-export.py` создаёт новый каталог `release/generated/public-pl` с manifest и не переносит историю Git. Отчёт аудита остаётся в `release/private` и не входит в публикуемые файлы.
